  - [ ] Capacity (supply side): Employee gains base availability (FTE), contracts (start/end/permanent), leave and a public-holiday calendar, behind an effective-capacity service computing per-person, per-period capacity (leave and holidays subtracted).   - [ ] Demands: client/project, expected start/end, FTE required, status as a sales-funnel stage, source. Seam to what already exists: Estimate/Lead probability → forecast (soft) demand; accepted work → committed demand; de-allocating a resource returns its demand to the unmet pool (upstream's core workflow).
  - [ ] Allocations: rows of (employee, project or task, FTE/percent, status Proposed→Committed, source Manual/Imported) as a new table beside `project_staff` (undated, rate-only — stays the costing seam). Percentage-across-a-project is the primary mode — the common model for low-maturity clients who just want a body, and the way both existing pieces of work in the DB run: an `allocation_percent` of the person's capacity over the project's span, no per-date detail required. Task-level/per-date FTE is the richer mode on top, not a prerequisite. Per-resource and per-project allocation views (upstream's org/project alloc reports) and a capacity-vs-demand heat map with utilisation targets.
  - [ ] What-if step 1 — manual scenario sandbox (the "multiple attempts" concept, before any solver): a scenario container seeded from the current allocations; add/edit/remove allocation rows by hand — percentage-across-project first-class — with live readouts recomputed as you edit (utilisation/over-allocation per person per period, demand left unmet, skill-match warnings). Ends in exactly two ways: discard (throw the scenario away, nothing touched) or commit (its allocation set becomes the real rows, superseding what it replaced). No solver yet — this alone is the what-if for the body-hire percentage world.
  - [ ] What-if step 2 — deterministic scoring and comparison: the score (skill-match coverage from the employee_skill/service_skill matrices, capacity fit vs FTE per period, demand coverage, continuity) computed per scenario and shown side by side, so "acceptable" is a number, not a vibe; feeds manual review now and solver ranking later.
  - [ ] What-if step 3 — solver-assisted suggestions: per-demand best-fit suggestions offered inside a sandbox (greedy skill + availability match, click to accept/reject each); human stays in the loop, the solver widens from here.
  - [ ] What-if step 4 — automated attempts (the NP-hard core): generate multiple candidate allocation attempts per scenario via local search / simulated annealing with restarts (multi-skill resource-constrained scheduling is NP-hard — [MDPI Algorithms, MSRCPSP](https://www.mdpi.com/1999-4893/19/9/738)); each attempt persisted with its score and compared, iterate until one is acceptable, then commit flips that attempt's allocations Proposed→Committed. Solver runs bounded (time/iteration caps, queued job) — never an unbounded loop.
